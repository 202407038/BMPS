# Implementation Plan: BMPS

## Overview

TypeScript 기반 React 클라이언트와 HTTP/WebSocket 서버를 공통 도메인 계약, PostgreSQL, Redis, S3 호환 객체 저장소 위에 단계적으로 구현한다. 먼저 공통 계약과 테스트 기반을 동결하고, 세션·의견/파일·분석 기능을 서로 다른 소유 경계에서 병렬 개발한다. 이후 재접속·패널·보존/삭제를 연결하고 실제 의존성을 사용하는 통합 및 E2E 테스트로 릴리스 후보를 검증한다.

5인 팀은 `팀장(사용자)`, `개발자 A`, `개발자 B`, `개발자 C`, `발표·지원 담당`으로 운영한다. 팀장은 아키텍처와 공통 계약, 작업 갈래, 리뷰와 통합을 책임지되 개별 기능 구현은 개발자 A·B·C에게 위임한다. `발표·지원 담당`은 전반부에 독립적이고 위험이 낮은 UI·테스트 지원 코드를 구현하고, 기능 통합 준비 이후에 발표와 데모 준비로 중심 업무를 전환한다.

## 역할과 기능 소유권

| 역할 | 주 책임 | 수정 경계와 협업 원칙 |
|---|---|---|
| `팀장(사용자)` | 아키텍처·기술 선택, 공유 타입/API/DB 계약, 작업 갈래 결정, PR 리뷰, 메인 통합, 통합/E2E 최종 판정 | `packages/contracts`, 초기 DB 계약과 최종 연결을 소유한다. 기능 담당자의 코드를 대신 구현하지 않고 계약·통합 병목만 해결한다. |
| `개발자 A` | 익명 주체, 세션 생성·입장, 접속 상태, WebSocket 세션 구독, 재접속 동기화, 보존 만료 | `apps/server/src/features/sessions`, `presence`, `sync`, `retention`과 대응 테스트를 우선 수정한다. |
| `개발자 B` | 텍스트·링크·파일 의견, 객체 저장·열람 API, 삭제 권한과 파일 정리 | `apps/server/src/features/items`, `files`, `deletion`과 대응 테스트를 우선 수정한다. |
| `개발자 C` | 분석 스냅샷·결과·재분석 계보, 확인 요청·반응, 기능별 패널 데이터 연결 | `apps/server/src/features/analyses`, `reactions`와 `apps/web/src/features`의 기능 연결 코드를 우선 수정한다. |
| `발표·지원 담당` | 공통 패널·빈 상태·오류 UI, 링크/파일 열람 UI, fixture·mock, 접근성·문구, 데모 seed 데이터 | `apps/web/src/components/shared`, `packages/test-support`, `tools/demo-seed`를 우선 수정한다. 핵심 DB·동시성·보안·분석 계보 로직은 수정하지 않는다. |

개발자 A·B·C는 각자 소유한 기능 디렉터리와 테스트를 우선 수정한다. 공유 타입, API 스키마, DB 마이그레이션, 공통 이벤트 형식을 변경하려면 구현 전에 `팀장(사용자)`의 승인을 받는다. 기능 간 연결이 필요하면 소비자가 임시 계약을 만들지 않고 계약 소유자에게 변경을 요청한다.

## 협업 단계와 발표 전환

- **Wave 0–2:** 전원이 프로젝트 기반과 계약 검토에 참여한다. `발표·지원 담당`은 fixture·mock과 공통 빈 상태/오류 UI를 구현한다.
- **Wave 3–6:** 개발자 A·B·C는 소유한 기능 묶음을 병렬 구현한다. `발표·지원 담당`은 링크/파일 열람 UI, 패널 공통 컴포넌트, 컴포넌트 테스트, 접근성·문구와 데모 seed 코드를 맡는다.
- **기능 통합 준비 체크포인트 이후:** `발표·지원 담당`은 코드 소유권을 유지하되 중심 업무를 PPT·발표 구성과 데모 자료 준비로 전환한다. 이 비코딩 활동은 구현 체크박스에 넣지 않으며, 확정된 구현과 검증 결과만 자료에 반영한다.
- **Wave 7:** `발표·지원 담당`은 E2E 데모 경로 검증과 seed 데이터 보완을 지원하고, `팀장(사용자)`의 최종 판정에 필요한 재현 절차를 제공한다.

## 브랜치 전략과 PR 기준

### 브랜치 전략

- `main`은 보호 브랜치로 유지하며 직접 커밋하지 않는다. 최종 병합 권한은 `팀장(사용자)`에게 둔다.
- 각 하위 작업은 최신 `main`에서 시작한다. 구현은 `feature/<task-id>-<topic>`, 테스트는 `test/<task-id>-<topic>`, 지원 UI는 `support/<task-id>-<topic>` 형식을 사용한다.
- PR 하나는 원칙적으로 하위 작업 하나만 포함한다. 같은 기능의 구현과 인접 테스트를 합쳐야 하면 PR 설명에 결합 이유와 영향 파일을 적는다.
- 공유 계약 변경은 별도 PR로 먼저 병합한다. 기능 브랜치에서 공유 계약을 복제하거나 기능별 변형을 만들지 않는다.
- 개발자 A·B·C는 자신의 기능을 직접 구현하고, `팀장(사용자)`은 계약 리뷰와 메인 통합을 수행한다. 팀장 브랜치에 기능 구현을 몰아넣지 않는다.
- `발표·지원 담당`의 코드는 공통 UI와 테스트 지원 경계 안에 둔다. 서버 권한, 용량 잠금, Redis 원자 연산, 분석 계보 변경은 해당 기능 담당자에게 넘긴다.

### PR 승인 기준

- PR 설명에 작업 ID, 관련 요구사항 번호, 변경 범위, 검증 명령과 결과, 위험 요소와 되돌리기 방법을 기록한다.
- 필수 구현 작업은 관련 자동화 테스트와 정적 검사에 통과해야 한다. `*`가 붙은 선택 테스트를 생략하면 생략 사실과 남은 위험을 기록한다.
- 공유 계약·마이그레이션·이벤트 형식 변경은 `팀장(사용자)`의 사전 계약 확인과 최종 승인을 모두 받아야 한다.
- 일반 기능 PR은 다른 개발자 1명의 리뷰와 `팀장(사용자)`의 통합 승인을 받는다. 작성자는 자신의 PR을 단독 승인하지 않는다.
- 보안, 권한, 파일 접근, 동시성, 데이터 삭제 변경은 표기된 협업 담당자가 추가로 리뷰한다.
- `발표·지원 담당`의 UI PR은 해당 데이터를 소유한 개발자 A·B·C 중 1명이 동작과 문구를 확인한다.
- 병합 전에 충돌을 해결하고 해당 웨이브의 모든 선행 작업이 `main`에 반영됐는지 확인한다.

## 인터페이스 동결과 변경 관리

- **동결 시점:** Wave 2가 끝나고 계약 동결 체크포인트를 통과하면 TypeScript 공유 타입, Zod 스키마, HTTP/WebSocket 메시지, 오류 코드, idempotency 규칙, DB 키·관계, 저장소·Redis·분석 포트를 기준선으로 동결한다.
- **동결 전:** 개발자 A·B·C는 자신의 소비 관점에서 계약을 검토하고 누락된 필드, 권한 경계와 이벤트 순서를 제안한다. `발표·지원 담당`은 UI 상태와 mock 작성 가능성을 검토한다.
- **동결 후:** 변경 제안은 별도 계약 PR에 영향 요구사항, 호환성, 마이그레이션, 소비자 수정 목록을 기록한다. `팀장(사용자)`이 작업 갈래와 병합 순서를 결정하고 모든 소비자 승인을 확인한다.
- **병렬 개발 규칙:** 동결된 포트의 mock으로 기능을 개발하고 다른 담당자의 내부 모듈을 직접 import하지 않는다. 기능 간 통합은 `packages/contracts`의 계약과 공개 어댑터만 사용한다.

## Notes

- `*`가 붙은 하위 작업은 선택 가능한 테스트 작업이며, 핵심 구현 작업을 완료한 뒤 수행한다. 필수 구현 범위와 요구사항 추적성은 선택 여부와 관계없이 유지한다.
- Property 1–21은 각각 별도 fast-check 테스트 파일로 작성하고 최소 100회 실행한다. 병렬 웨이브에서 같은 테스트 파일을 동시에 수정하지 않는다.
- 통합·E2E 테스트는 격리된 PostgreSQL, Redis, S3 호환 저장소와 독립 브라우저 컨텍스트를 사용한다.
- 업무량은 개발자 A의 세션·접속·동기화·보존, 개발자 B의 의견·파일·삭제, 개발자 C의 분석·반응·기능 패널 묶음으로 나눈다. 공통 기반과 최종 병합만 팀장이 소유한다.
- `발표·지원 담당`은 전반부에 실제 코딩 업무를 수행한다. 기능 통합 준비 체크포인트 뒤에는 PPT·발표 및 데모 자료 준비로 중심 업무를 전환하되, 비코딩 활동은 이 체크리스트에 추가하지 않는다.
- 체크포인트는 자동화 검증과 계약 상태를 확인하는 중단 지점이다. 체크포인트와 상위 작업은 의존성 그래프에 넣지 않는다.
